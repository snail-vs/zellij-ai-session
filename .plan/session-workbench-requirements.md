# 跨 Code CLI 的层级会话工作台：需求讨论稿

> 整理当前讨论，记录产品目标与尚未确定的设计选择。本文中的“子会话”只表示工作来源和导航关系，不表示 Agent 之间有主从、自动委派或验收关系。

## 1. 背景与痛点

Codex、Claude Code、OpenCode、Pi 等 Code CLI 都以线性聊天会话承载讨论和开发。一个复杂需求通常先讨论方案，再按步骤实施；实施中的代码、报错和临时问题会逐渐淹没原方案。之后要回到方案、处理另一个问题或继续下一步，都需要在很长的对话里找上下文。

希望将规划、各实施步骤及技术探索放在多个独立、可恢复的会话中。这些会话可以同时存在，用户能够随时切换并继续其中任意一个。创建新会话时，应方便地传入与当前工作有关的上下文，无须复制整段聊天。

## 2. 目标体验

```text
项目：某功能开发
└─ 方案讨论（Codex 原生会话 A）
   ├─ 第一步：调查现状（Claude Code 原生会话 B）
   ├─ 第二步：实现数据模型（Codex 原生会话 C）
   └─ 另一种方案探索（Pi 原生会话 D）
```

典型流程：

1. 在一个原生 Code CLI 会话里讨论方案。
2. 从该会话创建“第一步”子会话，选择使用哪个 CLI，并准备相关上下文。
3. 在同一个终端界面中进入新会话，实施时原方案会话仍可随时返回。
4. 随时打开统一导航器，切到任意已有会话继续聊天或工作。
5. 原生 CLI 进程仍在运行时，切回原进程；进程退出后，用该工具保存的会话恢复。
6. 完成一步后，其结果可以供后续会话使用；方案如需修改，由用户回到方案会话讨论。

“同一个终端界面”是重要要求：用户从当前 CLI 调出会话导航器，选中会话后，当前终端直接显示所选会话的原始 CLI 界面。用户不应为了切换工作而手工寻找或管理不同 tab、pane。底层是否使用 tab、pane 或 PTY，是实现细节。

## 3. 原生会话与工作台关系

### 项目与工作目录

`Project` 使用工作台生成的稳定 ID。第一版扫描到尚未归属项目的原生会话时，以该会话规范化后的实际工作目录自动建立项目，`root_directory` 为这个目录，初始名称为目录最后一段（例如 `/a/b/c` 对应 `c`）。同一个规范化工作目录的原生会话归到同一个自动项目，初始显示为项目下的根会话。用户也可以手动新建项目，并修改项目名称。

`Project.root_directory` 是项目的主目录，也是新建会话时的默认工作目录。第一版自动归属仅匹配**相同的规范化工作目录**，不递归吸纳子目录；手动创建项目后，也扫描并显示工作目录与其主目录相同的原生会话。以后可通过 `ProjectDirectory` 显式关联子目录、外部目录或 Git worktree；主目录始终由 `Project.root_directory` 唯一确定。

工具原生会话的 `directory` 是该 CLI 会话实际使用的工作目录。自动归属时它等于自动项目的主目录；用户后续手动整理或关联其他目录后，两者可以不同。已保存工作台信息的会话，其项目归属由保存的 `project_id` 确定，不随目录扫描结果改变。创建时选择的工作目录应与原生会话最终确认的实际目录区分；两者不一致时显示差异，不以目录代替原生会话 ID 进行关联。

### 工具原生会话

每个 Codex、Claude Code、OpenCode、Pi 会话继续由原工具创建、保存和恢复。即使两个会话使用同一种工具、同一个工作目录，它们在该工具中仍是两个独立的原生会话。保留工具原有的聊天界面、命令、权限交互及持久化行为。

### 会话身份及持久化

工作台不另造一层会话身份。会话键采用 `<tool>:<native_session_id>`，例如 `codex:<原生 ID>`；前缀用于区分不同工具，恢复工具对话时取出原生 ID。运行位置或进程 ID 只表示当前在哪里显示或运行，退出或重启后可能失效，不能作为会话键。

原生会话的列表、标题、实际目录和时间等仍由适配器扫描，工作台不复制原生历史。未保存工作台信息的扫描结果也显示为项目下的根会话。SQLite 中的 `Session` 只存需要持久化的工作台信息；为扫描到的会话建立父子关系时，按原生会话键补齐父、子行。树由扫描结果与这些稀疏记录合并得到：用户标题覆盖原生标题，已保存的项目和父子关系优先于目录自动归属。若原生会话暂时扫描不到，已保存的记录仍保留，并标明原生会话不可用；不可直接当作可恢复会话。

建议的数据关系如下：

```text
Project(id, name, root_directory, origin: auto | manual)
ProjectDirectory(project_id, path, kind: worktree | linked)  # 后续扩展
Session(id = "<tool>:<native_session_id>", project_id, parent_id?,
        title_override?, selected_cwd?, handoff_text?, handoff_path?,
        work_state?, created_at, updated_at)
PendingLaunch(request_id, parent_id?, project_id, tool, title, selected_cwd,
              handoff_text?, handoff_path?, state, started_at?, observed_pane?)
```

`Session` 的 `id` 是唯一会话键，`parent_id` 引用同表的会话键，只能指向同项目会话且不能形成循环。`PendingLaunch.request_id` 仅追踪一次创建操作，不是另一种会话 ID。运行位置可暂存在内存，使用前须重新确认；若以后持久缓存，也不能代替会话键。工作完成状态由用户维护，与运行进程状态分开。

新建子会话时先保存 `PendingLaunch`，启动 CLI 并确认这次启动产生的真实原生 ID，然后在一次事务中补齐父会话记录、写入子 `Session` 和 `parent_id`、清除待处理记录。启动失败、ID 未确认或进程中断时保留待处理记录；重试前先核对会话是否已经创建，避免重复创建或重复发送交接内容。同工具同目录的多个会话不能仅靠时间、目录或进程名称猜测对应关系；工具无法可靠提供 ID 时，要求用户从候选原生会话中明确选择。已有会话也可由用户手动设置父会话。是否提供“只规划、不启动”的操作留到后续版本。

## 4. 核心能力

### 统一入口与切换

- 在任意受管理的 CLI 界面中，用统一快捷操作打开会话导航器。
- 导航器展示项目、会话层级、工具、标题，以及能可靠确认的运行状态。
- 选中运行中的会话时，直接显示它已有的 CLI 进程，保留其当前画面、输入和正在进行的工作。
- 原进程已经退出时，使用其原生会话 ID 启动对应工具的恢复流程。
- 用户看到的是一个当前终端画面；切换不要求手工操作终端复用器的 tab 或 pane。

### 创建关联会话

- 在父会话中手动让模型写交接文档，或生成可供下一会话继续工作的文本。按 `Alt-S` 选中父会话后创建子会话；默认工作目录沿用父会话或使用项目主目录。
- 创建时输入标题、选择 Codex 或 OpenCode，粘贴交接文本或填写交接文档路径；第一版完成创建后直接启动新原生会话。
- 启动的是所选工具的全新原生会话，父会话继续独立存在。
- 将手动提供的交接内容发送为新会话的起始消息；使用文档路径时，起始消息明确要求新会话读取该文档。
- 捕获并关联新工具会话的真实 ID；创建失败或 ID 尚未取得时，应保留清晰的待处理状态。

### 会话整理

扫描到的既有原生会话自动显示在对应目录的项目下，可直接浏览、预览和恢复。若在其中一个会话上创建子会话，工作台保存两者的关系；无需用户先执行单独的“登记为根节点”操作。第一版允许选中已有会话，手动设为另一个已有会话的子会话，以处理启动后未能自动确认 ID 的情况。跨项目移动会话、批量整理和关联额外目录留待后续讨论。

## 5. 新会话的上下文衔接

跨工具衔接不能依赖某个 CLI 私有的聊天格式。第一版由用户在父会话中手动准备一份文档或一段**交接文本**，供新会话读取或作为起始消息，使其知道：

- 当前目标与工作范围；
- 依据的方案或决定，以及相关文件位置；
- 前一步已经完成的内容和仍未解决的问题；
- 工作目录或代码位置；
- 预期的产出与完成条件。

交接内容在创建子会话时由用户粘贴或填写文档路径，并可检查与编辑。工作台不自动总结父会话；新会话从干净的工具原生会话开始，通过起始消息读取或接收交接内容。同工具的原生 fork 可作为后续选项。

方案可能在子会话创建后改变，因此应能知道子会话建立时依据的是哪份方案、哪个版本或时间点。正在运行的会话不应在用户不知情时被注入新方案。步骤结果如何写回、保存在哪里，以及怎样提示其他会话读取，仍需细化。

会话分支与代码分支是两件事。多个会话可以使用同一个工作目录；需要同时修改同一代码时，可考虑为部分会话创建独立 Git worktree。是否创建 worktree 应由具体工作决定。

## 6. 界面展示与操作

第一版以现有 Zellij 插件的 `Alt-S` 浮窗为统一入口。打开后直接显示可展开的项目会话树和选中项预览；用户在同一个终端画面内完成选择，不需要手工寻找 tab 或 pane。浮窗应支持足够大的双栏布局，并根据终端尺寸调整显示方式。可调整尺寸或全屏的具体 Zellij 操作仍需验证。

```text
┌─ 项目与会话树 ─────────────┬─ 选中项预览 ────────────────────┐
│ ▾ Project A              │ 第一步：实现数据模型             │
│   方案讨论               │ Codex · 运行中 · /code/app       │
│   ▾ 第一步：实现数据模型 ◀│ 最近的原生会话内容：             │
│     数据结构探索          │ 用户：……                         │
│   第二步：前端导航        │ Agent：……                        │
│ ▸ Project B              │                                  │
└──────────────────────────┴──────────────────────────────────┘
```

| 操作 | 第一版行为 |
| --- | --- |
| `j`/`k`、上下键 | 在当前可见的项目和会话间移动光标 |
| 光标停在会话上 | 右侧只读预览该工具原生会话最近几轮用户与 Agent 对话，并显示工具、实际工作目录和可确认的运行状态 |
| 光标停在项目上 | 右侧显示项目名称、主目录和会话数量 |
| 回车停在会话上 | 运行中切到准确关联的原进程；已退出且原生会话可用则恢复；不可用时显示原因 |
| 回车停在项目上 | 展开或折叠该项目 |
| 左右键 | 折叠或展开有子会话的项目或会话 |
| `p` | 新建项目，名称和主目录从当前目录预填，可编辑 |
| `n` | 选中项目时创建根会话，选中会话时创建其子会话；填写标题、Codex/OpenCode、目录及交接文本或文档路径后创建并启动 |
| 待定快捷操作 | 为一个已扫描的会话手动设置父会话；禁止跨项目和循环引用 |

第一版的原生对话预览先支持 Codex 和 OpenCode。预览从它们各自的原生历史中只读提取，统一为用户和 Agent 消息；不复制或改写工具历史。现有 indexer 只有会话元数据，尚需增加按原生会话 ID 读取最近消息的适配器能力。预览不替代原生 CLI 的完整聊天界面；不支持预览、无法读取、尚未写入历史或待创建的记录，应分别显示明确的原因或交接说明，不能把空白误当成会话没有内容。其他工具现有的浏览和恢复能力不因预览范围收窄而移除。

### 运行底座的选择

现有 Zellij 插件具备浮窗入口、会话发现、聚焦运行 pane 和在新 tab/pane 恢复历史会话的基础路径，优先在此基础上验证第一版。其他运行底座仍可作为后续选项。

| 方案 | 与原生 CLI 融合方式 | 待验证点 |
| --- | --- | --- |
| Zellij 或 tmux 作为隐藏的运行底座 | 每个原生 CLI 在独立后台终端运行；统一导航器切换当前终端所显示的目标 | 能否做到顺畅的单画面导航、快捷键不冲突、后台进程持续运行 |
| 自己管理 PTY 和终端画面 | 工作台直接托管多个 CLI 进程并切换显示 | 终端渲染、输入转发、尺寸变化、滚动和权限提示的实现成本 |
| ACP 等协议接入 | 工作台通过统一协议管理受支持的 Agent 会话 | 各工具支持范围，以及保留原生 CLI 交互体验的程度 |

统一入口不依赖为每个工具分别增加 `/sessions` 命令。

## 7. 元数据与状态

工作台使用 SQLite 持久保存项目、必要的 `Session` 工作台信息、父子关系、待创建记录及交接材料引用。`ProjectDirectory` 是后续扩展。数据库独立于工具私有会话文件；原生会话元数据和历史继续由各工具保存和扫描，不复制到工作台数据库中。数据库文件的具体位置仍待确定。

状态需区分“工作是否完成”和“原生进程是否运行”。进程退出不等于工作完成；等待用户输入也不能仅凭终端暂时无输出判断。第一版优先显示可确认的信息，如尚未启动、进程仍在、进程已退出、用户手动标记完成。更细的工作状态依各工具可靠信号逐步增加。

## 8. 仍需讨论和验证

以下事项会影响第一版的操作流程或实现边界，实施前需要定型或完成技术验证：

1. 如何准确识别选中父会话及新建子会话的原生 session ID，并关联其运行 pane？同目录下多个同工具会话不能靠目录和进程名称推断；无法确认时应要求用户明确选择，并保留 `PendingLaunch`。
2. Codex、OpenCode 各自如何接收起始文本或文档路径？交接文本及文档路径如何持久保存、失败后如何重试而不重复发送？
3. 方案修订后，如何让相关会话明确感知变化？第一版不自动向运行中的会话注入新方案。
4. Codex 和 OpenCode 的第一版预览展示多少轮消息、何时刷新？当工具历史暂时不可读时，界面如何提示？
5. SQLite 数据库文件应存于用户数据目录、项目目录，还是两者分工？交接文档是否与数据库分开放置？
6. 现有 Alt-S 浮窗能否调整尺寸或切换全屏？切换能否保留原生 CLI 的画面和未提交输入？从插件取得“当前目录”时，应指向唤起它的 CLI pane，而非插件或 Zellij 自身的目录。
7. 多个 CLI 会话共享工作目录时，何时提示使用独立 worktree？除 Codex、OpenCode 之外的工具何时接入完整层级工作流？跨 Zellij session 或其他终端复用器支持做到什么程度？

## 9. 第一版验证重点

以 Codex 和 OpenCode 为首批工具，使用两个独立的原生 CLI 会话完成最小闭环：扫描到已有方案会话后自动建立目录项目并显示它；用户在父会话中手动准备交接文档或文本，按 `Alt-S` 选中父会话，创建实施子会话并发送交接内容；在树上移动光标时看到相应的原生对话预览；在两者之间反复切换，确认原进程与输入不丢失；退出其中一个 CLI 后，仍能从同一会话项恢复。这个闭环成立后，再扩展工具种类和状态能力。

## 10. 分阶段执行计划

每一阶段开一个新的实施会话，交接时提供本文件路径、当前阶段、上一阶段的结果与未解决问题。阶段按顺序推进；前一阶段的接口和风险确认后，下一阶段再依其实现。各阶段在同一仓库工作时先检查已有改动，避免覆盖其他会话的工作。

| 阶段 | 新会话的任务 | 可检查的完成条件 |
| --- | --- | --- |
| 0. 身份与运行验证 | 调查 Codex、OpenCode 新建会话时如何取得真实原生 ID；验证启动命令、起始消息、Zellij pane 与会话的准确关联，以及 Alt-S 浮窗尺寸和当前 CLI 目录来源。记录可用的确定性信号与无法自动确认时的手动流程。 | 形成逐工具的可复现验证记录和接口建议；明确哪些情况进入 `PendingLaunch`，不靠同目录、同工具猜 ID。 |
| 1. 持久化与合并 | 先按原生会话键聚合 Codex 分页历史，避免同一 `session_id` 产生重复扫描项；实现 SQLite `Project`、稀疏 `Session`、`PendingLaunch` 的读写和迁移；把扫描结果与工作台信息合并成一份视图；保存父子关系并校验同项目、无环。 | 重启后用户标题、项目归属、父子关系和待处理创建记录仍在；Codex 多页历史只显示一个原生会话；原生会话暂时扫描不到时有明确状态；原生历史不进入数据库。 |
| 2. 会话树与手动整理 | 将现有 Alt-S 导航改为项目会话树，支持展开、选择、项目创建和为已有会话设置父会话。先用现有扫描与持久化数据，不依赖自动创建子会话。 | 扫描到的根会话与手动关联的子会话在同一树中正确显示；错误关联会被拒绝；重新打开导航关系仍在。 |
| 3. 创建与交接 | 实现项目下新建根会话、会话下新建子会话；保存 `PendingLaunch`，启动 Codex/OpenCode，发送交接内容，确认真实 ID 后写入 `Session` 并关联父会话；处理失败、歧义和重试。 | 新会话只发送一次交接消息；成功后能从树里找到正确子会话；失败或无法确认 ID 时能查看待处理记录并安全恢复或手动关联。 |
| 4. 运行切换与恢复 | 利用已确认的会话与 pane 关联，在树中切到仍在运行的原进程；退出后按原生 ID 恢复。检查切换时原画面与未提交输入，避免把多个同目录会话指向同一 pane。 | 父子会话反复切换不丢输入；退出后恢复到正确原生会话；无法准确确认运行 pane 时给出明确提示。 |
| 5. 预览与闭环 | 为 Codex/OpenCode 增加按原生 ID 读取最近对话的只读预览，完成双栏布局与状态提示，并按第 9 节走完整体验。 | 预览显示真实最近对话；不可读、尚未写入及待处理状态各有明确提示；两工具均完成创建、切换、退出、恢复的闭环。 |

阶段 0 的调查结果、复现命令、接口建议及尚需交互验证的项目见 [phase-0-validation.md](phase-0-validation.md)。

### 首个阶段的产物与当前状态

本计划从 **阶段 0** 开始。它的产物是 [身份与运行验证记录](phase-0-validation.md)：逐工具列出原生会话 ID 的来源、启动和恢复命令、Zellij pane 与目录的可观测信号，以及无法确认 ID 时进入 `PendingLaunch` 并由用户手动关联的流程。该阶段是技术验证，不交付 SQLite 或会话树代码。

目前已完成源码、CLI 帮助、现有原生存储、索引器扫描和当前 Zellij pane 的只读验证。**尚未实际创建新的 Codex/OpenCode 会话并发送起始消息，也未在 Alt-S 浮窗里实测尺寸和唤起 pane 的目录**；这些项目在验证记录中标为未验证，因此阶段 0 的动态验证条件尚未全部满足。

如果“第一阶段”指编号 **1. 持久化与合并**，其预期产物是 SQLite 表及迁移、读写接口、Codex 分页历史按 `session_id` 聚合后的唯一会话列表、扫描结果与稀疏工作台记录合并的视图，以及同项目、无环的父子关系校验。重启后数据仍在且原生会话暂时缺失时有明确状态，是它的验收证据；这些代码目前尚未实施。
