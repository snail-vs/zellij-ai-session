## 1. 背景与痛点

Codex、Claude Code、OpenCode、Pi 等 Code CLI 都以线性聊天会话承载讨论和开发。一个复杂需求通常先讨论方案，再按步骤实施；实施中的代码、报错和临时问题会逐渐淹没原方案。之后要回到方案、处理另一个问题或继续下一步，都需要在很长的对话里找上下文。

希望将规划、各实施步骤及技术探索放在多个独立、可恢复的会话中。这些会话可以同时存在，用户能够随时切换并继续其中任意一个。创建新会话时，应方便地传入与当前工作有关的上下文，无须复制整段聊天。

## 2. 长期目标体验

```text
项目：某功能开发
└─ 方案讨论（Codex 原生会话 A）
   ├─ 第一步：调查现状（Claude Code 原生会话 B）
   ├─ 第二步：实现数据模型（Codex 原生会话 C）
   └─ 另一种方案探索（Pi 原生会话 D）
```

典型流程：

1. 在一个原生 Code CLI 会话里讨论方案。
2. 在所需的原生 CLI 中创建“第一步”会话，按需手动准备交接上下文。
3. 工作台扫描到新会话后，用户手动指定它的父会话；在同一个终端界面中查看会话树。
4. 随时打开统一导航器，切到任意已有会话继续聊天或工作。
5. 原生 CLI 进程仍在运行时，切回原进程；进程退出后，用该工具保存的会话恢复。
6. 完成一步后，其结果可以供后续会话使用；方案如需修改，由用户回到方案会话讨论。

“同一个终端界面”是重要要求：用户从当前 CLI 调出会话导航器，选中会话后，当前终端直接显示所选会话的原始 CLI 界面。用户不应为了切换工作而手工寻找或管理不同 tab、pane。底层是否使用 tab、pane 或 PTY，是实现细节。

## 3. 原生会话与工作台关系

### 项目与工作目录

`Project` 使用工作台生成的稳定 ID。扫描到尚未归属项目的原生会话时，以该会话规范化后的实际工作目录自动建立项目，`root_directory` 为这个目录，初始名称为目录最后一段（例如 `/a/b/c` 对应 `c`）。同一个规范化工作目录的原生会话归到同一个自动项目，初始显示为项目下的根会话。用户也可以手动新建项目，并修改项目名称。

`Project.root_directory` 是项目的主目录。当前自动归属仅匹配**相同的规范化工作目录**，不递归吸纳子目录；手动创建项目后，也扫描并显示工作目录与其主目录相同的原生会话。以后可通过 `ProjectDirectory` 显式关联子目录、外部目录或 Git worktree；主目录始终由 `Project.root_directory` 唯一确定。

工具原生会话的 `directory` 是该 CLI 会话实际使用的工作目录。自动归属时它等于自动项目的主目录；用户后续手动整理或关联其他目录后，两者可以不同。已保存工作台信息的会话，其项目归属由保存的 `project_id` 确定，不随目录扫描结果改变。不以目录代替原生会话 ID 进行关联。

### 工具原生会话

每个 Codex、Claude Code、OpenCode、Pi 会话继续由原工具创建、保存和恢复。即使两个会话使用同一种工具、同一个工作目录，它们在该工具中仍是两个独立的原生会话。保留工具原有的聊天界面、命令、权限交互及持久化行为。

### 会话身份及持久化

工作台不另造一层会话身份。会话键采用 `<tool>:<native_session_id>`，例如 `codex:<原生 ID>`；前缀用于区分不同工具，恢复工具对话时取出原生 ID。运行位置或进程 ID 只表示当前在哪里显示或运行，退出或重启后可能失效，不能作为会话键。

原生会话的列表、标题、实际目录和时间等仍由适配器扫描，工作台不复制原生历史。未保存工作台信息的扫描结果也显示为项目下的根会话。SQLite 中的 `Session` 只存需要持久化的工作台信息；为扫描到的会话建立父子关系时，按原生会话键补齐父、子行。树由扫描结果与这些稀疏记录合并得到：用户标题覆盖原生标题，已保存的项目和父子关系优先于目录自动归属。若原生会话暂时扫描不到，已保存的记录仍保留，并标明原生会话不可用；不可直接当作可恢复会话。

建议的数据关系如下：

```text
Project(id, name, root_directory, origin: auto | manual)
ProjectDirectory(project_id, path, kind: worktree | linked)  # 后续扩展
Session(id = "<tool>:<native_session_id>", project_id, parent_id?,
        title_override?, selected_cwd?, handoff_text?, handoff_path?,
        work_state?, created_at, updated_at)
```

`Session` 的 `id` 是唯一会话键，`parent_id` 引用同表的会话键，只能指向同项目会话且不能形成循环。先前实现的 `PendingLaunch` 表用于工作台内创建会话，当前不启用对应流程；它的 `request_id` 即使保留在数据库里，也不是另一种会话 ID。运行位置可暂存在内存，使用前须重新确认；若以后持久缓存，也不能代替会话键。工作完成状态由用户维护，与运行进程状态分开。

当前流程是先在原生 CLI 创建会话，再由工作台扫描，用户选中已有子会话并指定已有父会话。保存关系时按原生会话键补齐稀疏 `Session` 记录。同工具同目录的多个会话不能仅靠时间、目录或进程名称猜测父子关系；父会话由用户明确选择。

历史方案曾计划先保存 `PendingLaunch`，启动 CLI、捕获真实 ID，再写入子 `Session`；该工作台内创建流程随原阶段 3 于 2026-09-24 废弃，若将来重提须重新评估。

## 4. 核心能力

### 统一入口与现有打开能力

- 在任意受管理的 CLI 界面中，用统一快捷操作打开会话导航器。
- 导航器展示项目、会话层级、工具、标题，以及能可靠确认的运行状态。
- 选中会话时继续使用现有插件的打开或恢复路径；原阶段 4 对运行 pane 精确绑定和输入保留的增强验收已废弃，后续若需要应重新定义。
- 用户看到的是一个当前终端画面；切换不要求手工操作终端复用器的 tab 或 pane。

### 手动关联会话

- 用户在原生 CLI 中创建会话，工作台扫描后显示为根会话。
- 选中这个已有会话，使用 `m` 从同项目现有会话中指定父会话，也可清除父会话。关系只表达工作来源和导航层级。
- 工作台不在当前范围内创建原生会话、捕获新建 ID 或自动发送交接消息。

### 会话整理

扫描到的既有原生会话自动显示在对应目录的项目下，可直接浏览、预览和恢复。用户可将其中一个已有会话手动设为另一个已有会话的子会话；无需先执行单独的“登记为根节点”操作。跨项目移动会话、批量整理和关联额外目录留待后续讨论。

## 5. 新会话的上下文衔接

跨工具衔接不能依赖某个 CLI 私有的聊天格式。当前由用户在父会话中手动准备一份文档或一段**交接文本**，供新会话读取或作为起始消息，使其知道：

- 当前目标与工作范围；
- 依据的方案或决定，以及相关文件位置；
- 前一步已经完成的内容和仍未解决的问题；
- 工作目录或代码位置；
- 预期的产出与完成条件。

当前由用户在原生 CLI 中自行传入或读取交接文档，工作台只在扫描后记录父子关系。工作台不自动总结父会话，也不向原生会话注入消息。同工具的原生 fork 或工作台交接功能如将来需要，应另立需求。

方案可能在子会话创建后改变，因此应能知道子会话建立时依据的是哪份方案、哪个版本或时间点。正在运行的会话不应在用户不知情时被注入新方案。步骤结果如何写回、保存在哪里，以及怎样提示其他会话读取，仍需细化。

会话分支与代码分支是两件事。多个会话可以使用同一个工作目录；需要同时修改同一代码时，可考虑为部分会话创建独立 Git worktree。是否创建 worktree 应由具体工作决定。

## 6. 界面展示与操作

以现有 Zellij 插件的 `Alt-S` 浮窗为统一入口。当前已有项目会话树，接下来增加选中项右侧预览，并改善长列表导航。用户在同一个终端画面内完成选择，不需要手工寻找 tab 或 pane。双栏布局需根据终端尺寸调整；空间不足时仍应可读。

```text
┌─ 项目与会话树 ─────────────┬─ 选中项预览 ────────────────────┐
│ ▾ Project A              │ 第一步：实现数据模型             │
│   方案讨论               │ Codex · 运行中 · /code/app       │
│   ▾ 第一步：实现数据模型 ◀│ 最近的原生会话内容：             │
│     数据结构探索          │ 用户：……                         │
│   第二步：前端导航        │ Agent：……                        │
│ ▸ Project B              │                                  │
└──────────────────────────┴──────────────────────────────────┘
```

| 操作 | 当前或下一步行为 |
| --- | --- |
| `j`/`k`、上下键 | 在当前可见的项目和会话间移动光标 |
| 空格键 | 展开或收起选中的项目或有子会话的会话；会话叶节点不执行操作 |
| `←`/`→` | 折叠或展开选中的项目或有子会话的会话 |
| `C` / `E` | 一次折叠 / 展开所有项目；保留各会话自身的展开状态。折叠隐藏选中会话时，选中其所属项目 |
| `g` / `G` | 跳到当前树中第一条 / 最后一条**可见项**，并同步滚动位置 |
| `M` | 跳到当前树全部**可见项**的中位项，偶数项时取靠前一项；同步滚动位置 |
| 光标停在会话上 | 右侧只读预览该工具原生会话最近几轮用户与 Agent 对话，并显示工具、实际工作目录和可确认的运行状态 |
| 光标停在项目上 | 右侧显示项目名称、主目录和会话数量 |
| 回车停在会话上 | 沿用现有打开或恢复路径；原生会话不可用时显示原因 |
| 回车停在项目上 | 展开或折叠该项目 |
| `p` | 新建项目，名称和主目录从当前目录预填，可编辑 |
| `m` | 为选中会话从同项目已有会话中指定或清除父会话；禁止跨项目和循环引用 |

本轮原生对话预览先支持 Codex 和 OpenCode。光标移动到会话时，右侧展示该会话的标题、工具、目录、运行状态，以及最近的用户与 Agent 消息，效果参考用户提出的 Codex agents 会话预览。预览从各工具原生历史中按原生 ID 只读提取，统一消息角色和文本；不复制或改写工具历史。现有 indexer 只有会话元数据，需增加按原生会话 ID 读取最近消息的适配器能力。选中项目时右侧展示项目摘要。预览不替代原生 CLI 的完整聊天界面；不支持预览、无法读取或尚未写入历史时分别显示明确原因，不能把空白误当成会话没有内容。其他工具现有的浏览和恢复能力不因预览范围收窄而移除。

### 运行底座的选择

现有 Zellij 插件具备浮窗入口、会话发现、聚焦运行 pane 和在新 tab/pane 恢复历史会话的基础路径。其他运行底座仍可作为后续选项。

| 方案 | 与原生 CLI 融合方式 | 待验证点 |
| --- | --- | --- |
| Zellij 或 tmux 作为隐藏的运行底座 | 每个原生 CLI 在独立后台终端运行；统一导航器切换当前终端所显示的目标 | 能否做到顺畅的单画面导航、快捷键不冲突、后台进程持续运行 |
| 自己管理 PTY 和终端画面 | 工作台直接托管多个 CLI 进程并切换显示 | 终端渲染、输入转发、尺寸变化、滚动和权限提示的实现成本 |
| ACP 等协议接入 | 工作台通过统一协议管理受支持的 Agent 会话 | 各工具支持范围，以及保留原生 CLI 交互体验的程度 |

统一入口不依赖为每个工具分别增加 `/sessions` 命令。

## 7. 元数据与状态

工作台使用 SQLite 持久保存项目、必要的 `Session` 工作台信息和父子关系。先前实现的待创建记录是历史能力，当前不通过 UI 创建或使用它；`ProjectDirectory` 是后续扩展。数据库独立于工具私有会话文件；原生会话元数据和历史继续由各工具保存和扫描，不复制到工作台数据库中。

状态需区分“工作是否完成”和“原生进程是否运行”。进程退出不等于工作完成；等待用户输入也不能仅凭终端暂时无输出判断。当前优先显示可确认的信息，如进程仍在、进程已退出、用户手动标记完成。更细的工作状态依各工具可靠信号逐步增加。

## 8. 仍需讨论和验证

当前工作需要确认或实施时作出选择的事项：

1. `C`/`E`、`g`/`G`、`M` 是暂定快捷键；“中间项”暂按整张当前可见树的中位项定义，待用户反馈后可单独调整。
2. Codex 和 OpenCode 的预览展示多少消息、如何截断长消息、何时刷新，以及历史暂时不可读时的提示。预览读取应避免拖慢 `j`/`k` 连续移动。
3. Alt-S 浮窗可用宽度与高度；双栏放不下时采用怎样的单栏回退展示。

先前关于工作台内创建会话、自动捕获原生 ID、交接消息、运行 pane 精确绑定和切换原进程的开放事项，随原阶段 3、4、5 一并移出当前执行范围。需要重启时另立需求和验收条件。

## 9. 当前两项工作的验收重点

在已有项目会话树中选中 Codex、OpenCode 原生会话，右侧能显示对应会话最近对话；切换选中项时不会串到同目录的另一会话。无法读取时显示原因。项目选中时显示项目摘要。会话数超过一屏时，能够一次折叠或展开全部项目，并快速跳到首项、末项及约定的中间项；树重新计算后光标保持有效且滚动到可见位置。

## 11. 需求变化的文档维护规则

1. 本文件是**当前需求和阶段状态**的入口。新决定先在顶部变更记录写明日期、决定和受影响阶段，再修改相关正文；不要让正文同时保留互相冲突的“第一版”要求。
2. 已完成阶段的实施记录保留当时事实，不因需求变化而重写。废弃阶段保留编号、原目标和废弃原因；新任务使用新编号，便于回溯旧会话与提交。
3. 每个实施会话结束时新增或更新自己的阶段记录，至少写清：完成范围、验证证据、未完成项、已知限制、下一阶段可依赖的接口。主文档只维护决策与验收边界，避免重复抄写实现细节。
4. 交接给下一位 Agent 时只需提供本文件、目标阶段编号和上一阶段记录；若新发现改变需求，先更新变更记录，再调整阶段状态和验收条件。
